LAND RESERVATION SYSTEM - DATABASE SCHEMA NOTES
Report Date: May 12, 2026

=========================================
1. OVERVIEW
=========================================
The database supports a land marketplace with three main actors:
- Customers
- Land Owners
- Administrators

The active schema also includes personal profile details, utility metadata,
listing image galleries, direct messages, notifications, and platform settings.

=========================================
2. PRIMARY TABLES
=========================================

TABLE: users
-----------------------------------------------------------------------
Purpose: Custom authentication and role management.

Important fields:
- username
- role
- is_owner
- is_verified
- is_suspended
- created_on / updated_on

TABLE: accounts_personaldetails
-----------------------------------------------------------------------
Purpose: Extended profile information for each user.

Important fields:
- user_id
- fname / mname / surname
- address
- phone
- email
- photo_path
- bio

TABLE: accounts_systemsettings
-----------------------------------------------------------------------
Purpose: Admin-controlled global platform toggles.

Important fields:
- maintenance_mode
- email_notifications
- last_backup

TABLE: lands_land
-----------------------------------------------------------------------
Purpose: Stores each land listing for rent or sale.

Important fields:
- land_id
- owner_id
- title
- description
- region / district / ward / street / location
- latitude / longitude
- usage
- size / size_unit
- land_use
- topography
- soil_fertility
- utilities
- additional_utilities_notes
- price / price_unit
- weekly_discount / monthly_discount
- contact_phone / contact_email
- land_image_path
- is_active / is_draft
- wizard_step
- view_count

TABLE: lands_landimage
-----------------------------------------------------------------------
Purpose: Stores multiple images per land listing.

Important fields:
- land_id
- image
- position
- caption
- is_primary
- order

TABLE: lands_utility
-----------------------------------------------------------------------
Purpose: Utility and amenity catalogue plus optional direct utility records.

Important fields:
- name
- land
- description
- icon_class

TABLE: lands_reservation
-----------------------------------------------------------------------
Purpose: Booking requests, lifecycle status, and payment tracking.

Important fields:
- land_id
- customer_id
- customer_name / customer_email / customer_phone
- start_date / end_date
- status
- payment_status
- payment_method
- payment_reference
- payment_receipt
- payment_date
- payment_confirmed
- amount_paid
- agreed_price
- requested_size
- notes

TABLE: lands_wishlist
-----------------------------------------------------------------------
Purpose: Customer-saved listings.

Important fields:
- user_id
- land_id

TABLE: lands_message
-----------------------------------------------------------------------
Purpose: In-app communication between users.

Important fields:
- sender_id
- recipient_id
- land_id
- subject
- body
- is_read

TABLE: lands_notification
-----------------------------------------------------------------------
Purpose: System-generated notifications shown in the user interface.

Important fields:
- user_id
- notification_type
- title
- message
- link
- is_read

=========================================
3. KEY RELATIONSHIPS
=========================================

- One owner can have many land listings.
- One land listing can have many reservations.
- One land listing can have many gallery images.
- One land listing can be saved by many users through wishlist entries.
- One user can have many sent and received messages.
- One user can have many notifications.
- One user has one personal details record.
- Land and utility records are also linked through a many-to-many relation.

=========================================
4. APPLICATION-LEVEL LOGIC
=========================================

- Availability is calculated from reservation overlap and requested land size.
- Sale listings reduce remaining available size without date overlap logic.
- Rent listings use date ranges to calculate conflicts and remaining capacity.
- Payment proof can be submitted by customers and confirmed by owners.
- Listing reports and support requests are currently logged instead of stored in dedicated tables.

=========================================
5. INDEXES AND CONSTRAINTS
=========================================

- Reservation indexes exist for common availability and customer lookup queries.
- Wishlist has a unique `(user, land)` constraint.
- Usernames are unique.
- Land IDs are unique.
